# Experimental multi-context AOT

This change addresses the multi-context bootstrap part of [#15837](https://github.com/alibaba/nacos/issues/15837).
It is an opt-in experiment. The `native` Maven profile builds a platform-specific executable;
`release-native` packages it separately from the ordinary JVM distribution.
The default Maven build and ordinary JVM startup do not require generated AOT artifacts.

## What changes

- Generate separate initializers for core, web, console and enabled AI registry contexts.
  Preserve the existing deployment modes and parent relationships.
- Select each generated initializer explicitly when Spring uses AOT artifacts.
  JVM AOT requires the JVM system property `-Dspring.aot.enabled=true`;
  Native Image is detected automatically by Spring. The initializers are looked up by name, so
  the generator registers them for reflection without a condition (Spring's own hints for them
  require the application classes to be initialized, which this startup never does). It also
  registers every class generated directly as bytecode (CGLIB subclasses, class-based AOP proxies
  and FastClass helpers) with all member categories and unsafe allocation, because Spring's hints
  cover only part of what the runtime does with them.
- Check a structural manifest after Nacos environment plugins and before context refresh.
  It includes deployment, storage mode, datasource, profiles, function mode, protocol switches,
  resource search and selected SPI provider sets. It excludes ports, credentials and database URLs.
- Preserve default auth datasource initialization during AOT and register implicit `NacosForm`
  binding metadata, including inherited and optional setters. Preserve Naming metadata and list
  serialization even in server-only images.
- Bundle reachability metadata for the default Server combination (bundled plugins, MySQL and
  PostgreSQL drivers), so a Native build does not require tracing the Server first. See
  [Bundled reachability metadata](#bundled-reachability-metadata).

Changing plugins, conditional bean selections or deployment modes requires regenerating AOT
artifacts and rebuilding Native images. The manifest is not a complete fingerprint of all
configuration or plugin implementation versions. External datasource dialects, Mappers and JDBC
drivers must be present during generation and Native compilation. Ordinary JVM plugin loading
remains unchanged.

## Build and package with Maven

Set `JAVA_HOME` to a compatible GraalVM 25+ installation containing `native-image`, and install
its platform C toolchain. The existing `native` profile now builds from **Bootstrap**, replacing
the obsolete console-only Spring Boot AOT invocation. It forks a JVM for multi-context generation,
compiles generated Java, and combines directly generated bytecode and resources. Neither the
build helpers nor test dependencies are included in the Native application. It also works with
`-Dmaven.test.skip=true` when tests have been run separately.

Prepare a build configuration using the normal `application.properties` format. It only has to
carry the structural choices: `spring.sql.init.platform=postgresql` is a complete build
configuration for a PostgreSQL image (`mysql` for MySQL), plus the AI registry switches if those
contexts are wanted. Ports, database URLs and credentials belong to the runtime configuration.
Use a disposable build configuration, not production credentials. The reachability metadata for
the bundled plugins and the MySQL and PostgreSQL drivers ships with Bootstrap (see
[Bundled reachability metadata](#bundled-reachability-metadata)); additional plugins, JDBC drivers
or features must bring their own. Keep custom plugin JARs and metadata **outside `target`** when
using `clean`.

From the repository root:

```sh
mvn -B '-Pnative,release-native,!dev' -pl distribution -am clean package \
  -Dnacos.native.config=/absolute/path/build/application.properties \
  -Dnacos.native.metadata=/absolute/path/native-metadata \
  -Dnacos.native.plugins=/absolute/path/plugins \
  -Dnacos.native.deployment=merged \
  -Dnacos.native.standalone=true
```

The plugin directory is optional when only bundled plugins/drivers are needed. All additional
JARs in it, including transitive dependencies, participate in **both** AOT generation and Native
compilation. Maven runtime dependencies can also supply plugins. A plugin's own
`META-INF/native-image` metadata is read during Native compilation, but does not allow loading new
Java implementations into an already compiled executable. Rebuild after adding or upgrading a
plugin, JDBC driver, or Spring configuration.

| Property | Default | Purpose |
| --- | --- | --- |
| `nacos.native.config` | `distribution/conf/application.properties` | Configuration used during AOT generation |
| `nacos.native.deployment` | `merged` | `merged`, `server`, or `console`; requires rebuilding to change |
| `nacos.native.standalone` | `false` | Standalone or cluster Bean selection |
| `nacos.native.embedded-storage` | `false` | Explicit embedded storage selection |
| `nacos.native.plugins` | `bootstrap/target/native-plugins` | Additional plugin/driver JAR directory |
| `nacos.native.metadata` | `bootstrap/target/native-metadata` | Additional exercised Native metadata directory |
| `nacos.native.derby.experimental` | `false` | Explicit opt-in to the experimental Derby arguments below |
| `nacos.native.repository.enabled` | `true` | Adds the [GraalVM reachability metadata repository](#the-graalvm-reachability-metadata-repository) to the Native classpath; `false` leaves it out and the executable about 35 MB smaller |
| `nacos.native.options` | empty | Path of a Native Image argument file appended after the toolchain options, for example `--exact-reachability-metadata` for [diagnostic builds](#find-gaps-with-an-exact-mode-build) or `-march=compatibility` for an executable that must run on older CPUs |
| `nacos.native.build.heap` | `8g` | Maximum Native builder heap |
| `nacos.native.build.parallelism` | `2` | Native compiler parallelism |

Embedded Derby Server builds fail with an explanatory error unless
`-Dnacos.native.derby.experimental=true` is provided. This flag additionally requires the
experimental toolchain described below; it does not make ordinary GraalVM support runtime class
loading. Independent Console images do not embed the Server's database.

Outputs are `bootstrap/target/native/nacos-server` (or `.exe`) and an archive under
`distribution/target` named `nacos-server-<version>-native-<os>-<arch>`. The archive contains the
executable, companion native libraries when emitted, configuration templates, scripts, and the
structural AOT manifest. It excludes build tools, generated sources, tracing data, build
credentials and external plugin JARs. It is specific to the build platform, not a cross-platform
binary. Packaging requires a successful Native build; `release-native` alone is rejected.

On Linux/macOS, extract the archive, configure `conf/application.properties` with matching
structural choices and runtime authentication/database settings, then run:

```sh
NACOS_NATIVE_OPTS='-Xmx1g' bash bin/startup-native.sh
```

The launcher derives its home from its own directory and deployment defaults from the bundled
manifest. It runs the Native executable even if a JVM server JAR is also present. It does not use
`JAVA_HOME`; `NACOS_NATIVE_OPTS` accepts whitespace-separated Native VM flags. A mismatched
structural configuration is rejected by the application. Check `logs/startup.log` for readiness
and failures. Windows startup script support is not covered by this change.

To inspect AOT output and the Native command without running the expensive compiler, build only
Bootstrap with `-Pnative -pl bootstrap -am package -DnativeDryRun=true` and the same configuration
properties. A dry run does not produce a runnable binary or a release archive.

Ordinary JVM packaging still uses `mvn '-Prelease-nacos,!dev' clean install` and `bin/startup.sh`.
Its default classpath-based plugin loading and startup behavior are unchanged. The Native profile
is never activated implicitly by the JDK vendor or `JAVA_HOME`.

## Bundled reachability metadata

Bootstrap carries GraalVM reachability metadata in the unified format below
`src/main/resources/META-INF/native-image/`, in one `reachability-metadata.json` per owner (see
[Layout](#layout)). The `native` profile copies Bootstrap's classes into the Native classpath, and
Native Image reads every `reachability-metadata.json` below `META-INF/native-image`, so it needs no
further configuration. An ordinary JVM never reads the files, and the JVM artifact contract does
not depend on them. They hold only what the build does not get from another source (see
[below](#what-the-build-gets-elsewhere)).

### Layout

Each file belongs to one owner, as a library ships the metadata of its own classes, in
`META-INF/native-image/<groupId>/<artifactId>/`:

- `com.alibaba.nacos/nacos-bootstrap`: the classes and resources of Nacos itself, from every module.
- `<groupId>/<artifactId>`: the classes and resources of one third-party artifact, for example
  `org.postgresql/postgresql`, `org.apache.tomcat.embed/tomcat-embed-core` or
  `org.springframework.boot/spring-boot`.
- `jdk/runtime`: the classes of the JDK that Nacos or a library reaches by reflection.

The owner of an entry is the artifact whose jar on the Native classpath contains the class or the
resource; of several jars with the same class, the first on the classpath owns it. A proxy belongs
to Nacos if one of its interfaces does, otherwise to the owner of its first interface that is not a
JDK type. A resource that several jars hold, such as a `META-INF/services` file, is written once:
to Nacos if Nacos has it, otherwise to the first jar that does. `refresh` places the entries and
removes the file of an owner that has none left, so nobody moves entries by hand, and
`check --classpath` verifies the placement.

The folders carry no version. The versions of the dependencies come from one managed set and change
with it, so a versioned folder would have to move with every bump, and GraalVM does not look at the
names of folders.

### What it covers

The files record the dynamic access that neither static analysis nor Spring AOT can see in the
default Server, as exercised by the standalone OpenAPI, Java SDK and Maintainer SDK integration
suites: the bundled default plugins and their SPI providers, the bundled MySQL and PostgreSQL
JDBC drivers and the HikariCP pool, the gRPC payload and model classes that Jackson reaches
reflectively, JRaft and Netty, and resources and resource bundles that are looked up by name.

The suites reach the state of the Raft groups only in part. JRaft saves a snapshot of a group long
after the start and loads it only when the Server starts again, and a suite never creates some kinds
of data: a service with a label selector or with the MYSQL health checker, a held lock, a naming
switch that is replicated. The bundle covers the Hessian and Jackson payloads of these cases as
well. They were serialized and read back through the serializers of the Server on a JVM under the
tracing agent, and a Native executable that saw only the bundled metadata printed what the JVM
printed. The Native CI job asks JRaft for snapshots every 30 seconds, so the code that saves them
runs in every job, and it restarts the Server once after the suites, so that the code that loads a
snapshot and replays the log behind it runs with data of its own.

It was traced on standalone, merged-deployment Servers with an external datasource, which is also
the combination the [Native CI job](#the-native-ci-job) validates. It does **not** cover embedded
Derby (see [below](#native-scope-and-derby-compatibility)), Oracle, third-party plugins or
drivers, the AI registry contexts (`nacos.ai.mcp.registry.enabled`,
`nacos.ai.skill.registry.enabled`, `nacos.ai.ard.enabled`), the Istio, Kubernetes sync and DNS
adaptors, the cluster-only paths between nodes, the probing of an instance by the Server with the
MYSQL health checker, or a label selector with a CMDB behind it. Whoever enables one of these
supplies the missing metadata through `nacos.native.metadata` or in the plugin's own
`META-INF/native-image`, and validates the result.

### What the build gets elsewhere

The Native build reads reachability metadata from more places than these files:

- The jars of the classpath, as far as they ship `META-INF/native-image` files and
  `bootstrap/src/test/resources/aot/native-image.args` does not exclude them. It excludes the old
  trace in the jar of `nacos-console`.
- The files that the AOT generator writes for the application contexts, in
  `bootstrap/target/native/aot`.

The files repeat none of what these sources provide. `refresh` takes it out of the entries, and an
entry that they provide in full altogether; `check --classpath` reports what repeats them. Only an
entry without a condition counts as provided. An entry with a `typeReached` condition is available
once its type is reached, and the access that the bundled entry serves may come before.

### The GraalVM reachability metadata repository

The `native` profile adds the [GraalVM reachability metadata repository][metadata-repository] to the
Native classpath, in the release that `graalvm-reachability-metadata.version` of the root `pom.xml`
names. It helps with the libraries of the Server: when a dependency is added or changes, the
community metadata for it applies without a refresh, as far as the repository has it. The
`native-maven-plugin` adds the repository only to a classpath that it builds itself, and this build
passes the exact one in `classpath.args`. So the profile runs the plugin's
`add-reachability-metadata` goal, which copies the configuration of the artifacts of the module to
`bootstrap/target/native-reachability`, and the Ant step that writes `classpath.args` puts that
directory on it. The directory is not `target/classes`, because a file of the repository and a
bundled file of the same artifact have the same name.

The files do not rely on the repository, and `refresh` takes nothing out for it, so a build with
the repository and a build without it both work, and a new release of it needs no refresh. It
guards nearly all of its entries with a `typeReached` condition, and a guard may be reached later
than the access that the Server needs it for. The repository guards the methods of
`com.alibaba.nacos.api.naming.pojo.healthcheck.impl.Mysql` with `HealthCheckerFactory`, which a
Server that loads its persistent services from a Raft snapshot does not reach: a bundle without the
entry of `Mysql` failed the restart check of the [Native CI job](#the-native-ci-job) with a missing
registration, and a bundle that relied on the repository would fail the same way.

The repository costs about 35 MB: the executable of the Native CI job is 288 MB with it and 253 MB
without it (GraalVM CE 25.2.4). To leave it out, build with
`-Dnacos.native.repository.enabled=false`. The plugin downloads the release from GitHub into
`bootstrap/target/graalvm-reachability-metadata` and reuses it until `clean`. A build without access
to GitHub leaves the repository out, or sets `<url>` or `<localPath>` in the `metadataRepository` of
the `add-reachability-metadata` execution in `bootstrap/pom.xml` to a copy of
`graalvm-reachability-metadata-<version>.zip`.

[metadata-repository]: https://github.com/oracle/graalvm-reachability-metadata

### What it leaves out

`test/scripts/native-metadata.py` applies these rules each time the files are refreshed, and `check`
enforces them in CI:

- Classes that Spring AOT generates during the build (`$$SpringCGLIB$$` subclasses and
  `__BeanDefinitions`, `__ApplicationContextInitializer` and similar). The build derives their
  names from the generated output, either through Spring's hints or through the registrations of
  the generator described above, so a static copy would be redundant and would go stale.
- Agent and JVM internals: JVM diagnostic commands, JFR management, `jdk.internal.*`, Native Image
  builder classes and test frameworks.
- Lambda classes, the `{"type": {"lambda": ...}}` entries. The GraalVM 25 documentation states that
  metadata cannot be provided for lambda-proxy classes, and a probe with GraalVM CE 25.0.2 showed
  that such an entry changes nothing that reflection on the class finds, with or without member
  flags. A build with `--exact-reachability-metadata` reports these classes anyway. The Server's
  four reports come from Spring checking infrastructure beans for advisors, and the default and the
  exact build pass and fail the same tests. `collect-missing` counts and skips them.
- Lookups of classes and resources that do not exist on the Native classpath, such as probes for
  optional libraries or locale variants like `LocalStrings_zh_CN.properties`. They describe the
  machine that was traced, and the default reachability mode does not need them. A build with
  `--exact-reachability-metadata` reports them anyway; ignore reports for names that do not exist.
- Anything that identifies a machine or a person, such as absolute paths, host names and
  addresses. `check` rejects them.

Entries are sorted and written one per line, so a refresh produces a reviewable diff. Run
`python3 test/scripts/native-metadata.py check` to verify the committed files. Adding
`--classpath bootstrap/target/native/classpath.args` also reports entries whose class, resource or
condition type disappeared, for example after a rename, and entries that sit in the file of another
owner. The ordinary CI step `native-build-it.py` runs the tool's self test and the classpath-free
check.

### Conditions

Every entry is guarded by a `typeReached` condition, as GraalVM recommends, so that metadata only
enters an image that contains the code that needs it. The builder includes a conditional entry if
its type is reachable at build time, and the executable makes the entry available once that type
is reached: right before the initialization of its class starts, or of a subtype. Until then every
dynamic access that the entry serves behaves as if the entry did not exist, so a condition type has
to be initialized before the first access that the entry serves. A type that is only named by a
class literal is never initialized.

The condition depends on the owner of the entry:

- Nacos and the JDK (`com.alibaba.nacos/nacos-bootstrap`, `jdk/runtime`):
  `com.alibaba.nacos.bootstrap.NacosBootstrap`, the main class of the Native executable, which is
  initialized before any other Server code runs. The JDK classes are in the metadata because the
  libraries of the Server reach them, not because one part of the Server does.
- A third-party artifact: the type that makes the Server use it. That is often not a type of the
  artifact itself, because something else looks up the classes of an artifact before any of them is
  initialized. On a start of the Server, `HikariConfig` loads the PostgreSQL driver by name before
  `org.postgresql.Driver` is initialized, and Spring Boot looks up the classes of Tomcat, Jackson
  and Micrometer while it builds the application context. `CONDITION_GROUPS` in
  `native-metadata.py` holds the table, with the reason for each row. In short:
  - `org.springframework.boot.SpringApplication`: every artifact of the Spring family, and the
    libraries whose classes Spring Boot looks up (Tomcat, Jackson, Micrometer, Reactor, HikariCP,
    gRPC API, AspectJ, Kotlin and others);
  - `com.zaxxer.hikari.HikariConfig`: the JDBC drivers;
  - `org.slf4j.LoggerFactory` for SLF4J and logback-classic, `ch.qos.logback.classic.LoggerContext`
    for logback-core;
  - the type that loads or initializes the library, for JRaft, Hessian, protobuf, the Disruptor,
    gRPC (`NameResolverRegistry`, `LoadBalancerRegistry`, `NettyServerBuilder`), Guava, JCTools and
    dnsjava.

The guard keeps the metadata out of an image that does not contain what needs it. It does not make
the Server's own executable smaller, because the Server needs all of it.

A row of the table is checked against a run of the Server. `native-trace-server.sh classlog`
starts the Server on a JVM with the classpath of the Native build and writes the order in which
classes are loaded and initialized to a log; `test/scripts/native-condition-order.py` checks, for
each owner, that the condition type is initialized before the first class of its entries is used.
Run the smoke test and the restart check, as the Native CI job does, and give the script the log of
the start and the log of the restart. For the metadata in this repository 73 of the 79 third-party
owners were confirmed that way. The other six:

- For two, Guava and JCTools, a comparison of load times shows nothing: their entries are
  package-private superclasses of the condition type, which look up their fields in static
  initializers that only run as part of the initialization of that type. GraalVM reaches a type
  right before that starts, as the `SuperType` example in its documentation of conditions shows, so
  those two are accepted for that reason.
- Three, dnsjava, HttpClient and RocksDB, have only resource entries, and a class log does not show
  when a resource is read. The agentscope extension was not used by the run. The types of these
  four are early ones.

The comparison covers the classes of the reflection entries on the paths of the run. The `exact`
variant of the Native CI job reports every access without available metadata, a resource and an
entry whose condition is not reached yet included, so it covers what the suites and the restart
check exercise; a path that none of them exercises is as uncovered as before.

`refresh` sets the condition of every entry from its owner, whatever the inputs carry, so that a
trace, the report of an exact-mode build and the committed files can be mixed freely. It stops at
an owner without a row: add the owner to `CONDITION_GROUPS` after the comparison above. `check`
rejects an entry that another condition guards and an owner without a row, and it fails when the
source of the main class is gone, because renaming `NacosBootstrap` would otherwise leave the
entries of Nacos and of the JDK guarded by a type that does not exist. After such a rename, update
`SERVER_ENTRY_POINT` in `native-metadata.py` and the conditions in the bundled files.

### Refresh the bundled metadata

Refresh the metadata when the Server's dependencies, plugin SPI providers, reflectively serialized
model classes or reflective code paths change, and review the result like source code. Use
GraalVM 25+ (`JAVA_HOME` must contain `native-image`) and disposable databases and homes.

1. Prepare the AOT output and the exact classpath of the Native build. Compilation is not needed:

   ```sh
   mvn -B '-Pnative,!dev' -pl bootstrap -am package -DnativeDryRun=true \
     -Dnacos.native.standalone=true -Dnacos.native.config=/absolute/path/build.properties
   ```

2. Start the AOT application under the tracing agent. The script reads the classpath and the
   structural configuration from the build output. The trace directory must be absolute and
   outside the source tree; the script fixes an English locale so that the trace does not depend
   on the machine:

   ```sh
   bash test/scripts/native-trace-server.sh output /absolute/path/trace /absolute/path/nacos-home
   ```

3. Exercise the Server. Bootstrap the administrator and the test identities with
   `test/scripts/auth-it-identity.sh bootstrap` and `prepare`, then run the OpenAPI, Java SDK
   and Maintainer SDK suites as `test/scripts/native-ci.sh` does, and open the Web console.
4. Stop the Server with `SIGTERM`, because the agent writes its output on exit. Start it again
   with `merge` instead of `output` against the same data, and repeat a few authenticated
   requests so that reads of persisted records are traced as well.
5. The datasource is a structural choice, so repeat steps 1 to 4 with `merge` into the same trace
   directory for every JDBC driver the metadata should cover.
6. Curate the trace together with the committed files:

   ```sh
   BUNDLE=bootstrap/src/main/resources/META-INF/native-image
   python3 test/scripts/native-metadata.py refresh \
     --classpath bootstrap/target/native/classpath.args "$BUNDLE" /absolute/path/trace
   ```

   The command merges all inputs, drops what the rules above exclude, takes out what the build
   gets elsewhere (see [above](#what-the-build-gets-elsewhere)), sets the condition of every entry
   from its owner (see [Conditions](#conditions)), sorts the entries into the files of their owners
   (see [Layout](#layout)), and rewrites the files below `BUNDLE`; it removes the file of an owner
   that has no entries left, and it stops at a new owner that has no condition type yet. Taking out
   what the build gets elsewhere needs the output of the build in step 1, `classpath.args` and the
   AOT files; `--provided-dir` names other directories of metadata files instead. Pass
   `--output-dir` to write below another directory, or `--output` for one merged file, which lists
   what an exact-mode build reports and does not take anything out. The committed files are an
   input as well, because some of their entries are in no trace: the reports of an exact-mode build
   (see below), and the accessors that protobuf looks up on a generated message and on its
   `Builder`, which the agent does not record because it records only the methods that are
   invoked. The ones of JRaft's
   `SnapshotMeta` matter: JRaft turns the message into text when it loads a snapshot. A refresh
   from the trace alone drops these entries, and a restarted Native Server stops coming up; the
   restart check of the [Native CI job](#the-native-ci-job) fails when that happens.
7. If the dependencies changed, check the condition types against a run of the Server, as
   described under [Conditions](#conditions), and validate the result against the Native
   executable, as described next.

### Find gaps with an exact-mode build

A trace only contains what was exercised. To find what is still missing, build the executable with
`--exact-reachability-metadata` and run it with `-XX:MissingRegistrationReportingMode=Warn`: every
dynamic access without metadata is then reported instead of silently returning nothing. GraalVM
Community 25.0.2 stops an exact-mode build at some entries of the reachability metadata repository
("Bulk queries can only be set with 'name' ... run-time conditions"); 25.1.3 and later build it.
The Native CI job uses 25.0.4.

```sh
printf -- '--exact-reachability-metadata\n' > /absolute/path/exact.args
mvn -B '-Pnative,release-native,!dev' -pl distribution -am clean package \
  -Dnacos.native.config=/absolute/path/build.properties -Dnacos.native.standalone=true \
  -Dnacos.native.options=/absolute/path/exact.args
NACOS_NATIVE_OPTS='-Xmx1g -XX:MissingRegistrationReportingMode=Warn' bash bin/startup-native.sh
```

After exercising the executable, turn the reports in `logs/startup.log` into metadata:

```sh
python3 test/scripts/native-metadata.py collect-missing logs/startup.log --output /absolute/path/missing
python3 test/scripts/native-metadata.py refresh --classpath bootstrap/target/native/classpath.args \
  --output /absolute/path/delta.json /absolute/path/missing
```

`delta.json` lists what is missing and exists on the classpath. Pass it together with the original
trace to a final `refresh` to merge it into the bundled files. Each report names the exact class,
method or field. Repeat the cycle of exercising, collecting and merging until no relevant report
remains. Reports that the tool cannot parse are printed as `UNPARSED` and fail the `exact` variant
of the Native CI job; reports about lambda-proxy classes are counted and skipped, as described
above.

### The Native CI job

`.github/workflows/native-image.yml` builds the Native distribution on a GitHub-hosted runner,
starts it with `bin/startup-native.sh`, runs the smoke test (`test/scripts/native-smoke.sh`) and
the standalone OpenAPI, Java SDK and Maintainer SDK suites against the executable, restarts it once
with data of its own, and reports.
The datasource is a structural choice of the build, so every database is compiled on its own, in
two variants: `default` is the build that users get, and `exact` is the diagnostic build above.

- PostgreSQL runs every OpenAPI class.
- MySQL runs the Config, Naming, Core and Auth OpenAPI classes, which is enough to exercise its
  driver.
- The Java SDK suite runs the classes that need only a single, current Server. The upgrade
  migration, released-SDK compatibility and Jackson 3 scenarios need other setups and are not part
  of it. The Maintainer SDK suite runs as its profile defines it.

The Server is configured like the one in `.github/workflows/it-new.yml`, because the AI suites are
written for it: anonymous access to the AI APIs, small Remote Agent Discovery capacities and one
second reconciliation intervals for the MCP cutover and the search index. The job also passes
`-Dnacos.logs.path`, which keeps the log files below the Nacos home: an application that starts
from AOT output does not apply `-Dlogging.config` and would otherwise log to
`${user.home}/nacos/logs`.

The Raft snapshot interval is 30 seconds instead of 30 minutes. JRaft takes the first snapshot of
each group at a random time within the first interval, so a job of twenty minutes would reach the
code that saves the persistent naming data, the naming metadata and the locks only by chance.

The integration stage ends with a restart check. `test/scripts/native-restart.sh` creates data that
no suite creates: a persistent service with a label selector, a persistent instance in a cluster
with the MYSQL health checker, a naming switch that the Raft group replicates and a configuration.
The job waits for the snapshot timers, which fire every 30 to 60 seconds, stops the Server with
SIGTERM, starts it again on the same home and database, and looks for the data. The report stage
fails the job when a step failed, and it scans the logs of both runs for missing registrations.

Tests that fail for a reason that does not depend on the Native executable are listed in
`test/scripts/native-ci-baseline.txt`; they are reported but do not fail the job. At present these
are the tests that call the ARD adaptor on port 9080, which the default build leaves off because
`nacos.ai.ard.enabled` is a structural switch, and two Config list tests that also fail against
the ordinary JVM Server with PostgreSQL.

The workflow only calls the stages of `test/scripts/native-ci.sh` (`prepare`, `build`, `start`,
`smoke`, `integration`, `report`), so the same stages reproduce a job on any Linux host that has
GraalVM 25, Maven, Python 3, `curl` and `openssl`, and either `psql` with an empty PostgreSQL
database (`NATIVE_CI_DATABASE=postgresql`) or Docker for MySQL (`NATIVE_CI_DATABASE=mysql`, which
starts a disposable `mysql:8.4` container). The header of the script lists the variables.

The job installs GraalVM Community 25.0.4 (graal 25.2.4) with `version: '25.2'` of
`graalvm/setup-graalvm`. GraalVM Community ships as numbered innovation releases now, and a
`java-version` of `'25'` alone resolves to 25.0.2, the last `jdk-25.*` release.

On a GitHub-hosted runner with 4 vCPUs and GraalVM CE 25.2.4, the compilation takes between four
and six minutes and peaks at about 11.5 GB of resident memory with a 10 GB builder heap, so the job
uses GitHub-hosted runners instead of the self-hosted ones of the other Java checks. The executable
is 288 MB, or 253 MB without the reachability metadata repository. The Server answers its liveness
check about 1.5 to 2 seconds after it starts and holds about 470 MB after the suites.

The job runs for pull requests that touch the Native build and on demand. To run it on a fork
without opening a pull request, push a branch named `native-ci/<name>`.

## Build integration tests

After the ordinary `release-nacos` install, run `python3 test/scripts/native-build-it.py` with
`JAVA_HOME` pointing to JDK 17+. This CI check uses `skipNativeBuild=true` only to omit the Native
compiler; it executes real multi-context AOT generation and generated-source compilation on the
ordinary JDK. It verifies merged Derby, MySQL Server and PostgreSQL Console preparation, an external
SPI JAR in a directory with spaces, incremental configuration/Context replacement, explicit Derby
opt-in, release rejection for skipped/dry builds, and launcher argument handling. It also checks
that the ordinary JVM server JAR and classes are not contaminated by generated AOT/build tools.
Logs are retained in the printed temporary directory; `--work-dir` selects a fresh directory.

These build integration tests do not establish database or Native runtime compatibility. Validate
the packaged executable separately with the HTTP/SDK suites and persistence restarts below.

## Generate and run JVM AOT

Use JDK 17+ and Maven from the repository root. The generator is a **test utility**, compiled into
`bootstrap/target/test-classes`; it is neither included in the server jar nor run by the default
build. Execute it in a dedicated JVM because it closes build-time watchers and executors.

First build/install the project normally, including test compilation. Then obtain the runtime
classpath with the bundled development plugins (add any external plugin/driver jars to `CP`):

```sh
mvn -B clean install '-Prelease-nacos,!dev'
mvn -B -pl bootstrap -Pdev dependency:build-classpath \
  -DincludeScope=runtime -Dmdep.outputFile=target/aot-runtime-deps.txt
CP="$(pwd)/bootstrap/target/classes:$(cat bootstrap/target/aot-runtime-deps.txt)"
```

Create two disposable Nacos homes with `conf/application.properties`, using the normal configuration
format: `BUILD_HOME` for generation and `RUN_HOME` for runtime. Configure authentication secrets and,
for external storage, a dedicated database initialized with the matching Nacos schema. Do not use a
production database. Build/runtime structural choices must match; ports and database credentials
may differ. The example below uses standalone merged deployment with the configured datasource.
For enabled MCP, Skill or ARD protocols, configure the corresponding switches in both homes.

```sh
AOT_DIR="$(pwd)/bootstrap/target/aot"
java -Dnacos.standalone=true -Dnacos.deployment.type=merged \
  -Dnacos.home="$BUILD_HOME" \
  -Dspring.config.additional-location="file:$BUILD_HOME/conf/" \
  -cp "bootstrap/target/test-classes:$CP" \
  com.alibaba.nacos.bootstrap.NacosApplicationAotProcessor "$AOT_DIR"

# Include generated Java, directly generated bytecode (e.g. CGLIB), and resources.
mkdir -p "$AOT_DIR/compiled"
export AOT_DIR CP
python3 - <<'AOT_PY'
import os
from pathlib import Path
root = Path(os.environ['AOT_DIR'])
(root / 'sources.list').write_text('\n'.join('"' + str(p) + '"'
    for p in sorted(root.rglob('*.java'))))
outputs = [root / 'compiled', root / 'resources']
outputs += sorted(p for p in root.glob('*/*')
                  if p.is_dir() and p.name in ('classes', 'resources'))
(root / 'classpath.txt').write_text(os.pathsep.join(map(str, outputs))
                                  + os.pathsep + os.environ['CP'])
AOT_PY
AOT_CP="$(cat "$AOT_DIR/classpath.txt")"
javac --release 17 -parameters -cp "$AOT_CP" \
  -d "$AOT_DIR/compiled" "@$AOT_DIR/sources.list"
java -Dspring.aot.enabled=true -Dnacos.standalone=true -Dnacos.deployment.type=merged \
  -Dnacos.home="$RUN_HOME" \
  -Dspring.config.additional-location="file:$RUN_HOME/conf/" \
  -cp "$AOT_CP" com.alibaba.nacos.bootstrap.NacosBootstrap
```

For `server`, regenerate with `-Dnacos.deployment.type=server`. For an independent `console`,
regenerate with `console` and configure the remote Server and authentication normally. The console
must not create a local core/storage context. Do not put the test utility on the runtime classpath.
The generated index is `resources/META-INF/nacos/aot/initializers.properties`; do not hand-write it.

Verify both unset `spring.aot.enabled` and explicit `false` with these artifacts present, then
verify `true`. Use separate temporary homes/databases to avoid state leaking between runs.
Run the repository OpenAPI, Java SDK and Maintainer SDK integration suites against the running
server, including authenticated config writes, Naming metadata/list operations and optional form
fields. Health checks alone do not establish functional compatibility. For independent console,
verify UI assets and remote handler reads/writes as well.

## Reproduce the Native experiment

The default combination does not need this section: its metadata is
[bundled](#bundled-reachability-metadata). Use it to trace additional plugins, drivers or features
without Maven, or to see by hand what the helper scripts do.

Use a GraalVM installation compatible with the dependencies and a working C compiler. Start the
JVM AOT application with the Native Image agent, using the runtime flags above and a fresh
`TRACE_DIR` outside the source tree (`test/scripts/native-trace-server.sh` does the same with the
classpath and structural configuration of a finished `native` build):

```sh
"$GRAALVM_HOME/bin/java" \
  "-agentlib:native-image-agent=config-output-dir=$TRACE_DIR" \
  -Dspring.aot.enabled=true -Dnacos.standalone=true -Dnacos.deployment.type=merged \
  -Dnacos.home="$RUN_HOME" \
  -Dspring.config.additional-location="file:$RUN_HOME/conf/" \
  -cp "$AOT_CP" com.alibaba.nacos.bootstrap.NacosBootstrap
```

Exercise the selected HTTP/SDK/Console paths and wait for background initialization to finish
before stopping the process gracefully. When MCP is enabled, verify that lifecycle management
reaches `LIFECYCLE_MANAGED`; HTTP health alone does not cover that transition. Restart the traced
JVM with the same disposable data and `config-merge-dir=$TRACE_DIR` instead of `config-output-dir`
to capture persisted-record reads as well as first-start writes. Exercise authenticated requests
after restart. Refresh tracing when the application, dependencies or plugins change.

Confirm that `TRACE_DIR/reachability-metadata.json` is valid JSON. Do not commit a raw trace: it
is specific to the exercised plugin and deployment combination and contains machine specific
lookups. Changes to the bundled metadata go through `native-metadata.py refresh`, which applies
the rules described above. For the MySQL/PostgreSQL experiment with a raw trace, compile with:

```sh
"$GRAALVM_HOME/bin/native-image" --no-fallback -J-Xmx8g --parallelism=2 \
  @bootstrap/src/test/resources/aot/native-image.args \
  "-H:ConfigurationFileDirectories=$TRACE_DIR" \
  -cp "$AOT_CP" com.alibaba.nacos.bootstrap.NacosBootstrap "$AOT_DIR/nacos-native"
```

The argument file keeps Netty state initialized at runtime and excludes the old console-only
tracing snapshot. Generated Spring metadata and the newly exercised metadata remain included.
For the experimental Derby toolchain described below, additionally pass
`@bootstrap/src/test/resources/aot/derby-experimental.args` (the full experiment used a 10 GB
builder heap). These flags are only enabled by the explicit `nacos.native.derby.experimental` opt-in in
the Maven Native profile; ordinary Maven builds do not use them.
The persistence module supplies Native reflection metadata for the no-argument constructors of
Derby's storage format-ID classes, including checkpoint and transaction log records that
first-start tracing can miss. A unit test checks this list against the installed Derby registry.
These resources do not alter ordinary JVM execution.

Run the binary with matching structural configuration and a fresh runtime home/database:

```sh
"$AOT_DIR/nacos-native" -Xmx1g -Dnacos.standalone=true -Dnacos.deployment.type=merged \
  -Dnacos.home="$RUN_HOME" \
  -Dspring.config.additional-location="file:$RUN_HOME/conf/"
```

Repeat the functional tests against the binary and inspect logs for missing reflection/JNI
registrations and serialization failures. Restart repeatedly using the same disposable data to
verify checkpoint/log recovery and persisted authentication; do not erase Derby data between
restarts. Wait for login readiness, as the existing user cache first reloads after five seconds.
Compilation alone is not acceptance. Change the
deployment flag consistently in generation, tracing and execution for server-only or independent
console testing.

## Native scope and Derby compatibility

Native compilation additionally needs complete reachability metadata for the selected libraries,
plugins and business paths. The Maven Native profile uses the same multi-context generator. The experiment used generated Spring metadata plus GraalVM agent tracing
of authenticated HTTP and gRPC requests. Tracing only records exercised paths; this change does
not claim complete metadata for every API, third-party plugin or cluster configuration.
The opt-in Maven packaging does not establish full API, plugin or platform certification.

| Runtime / database | Investigation result |
| --- | --- |
| Ordinary JVM or JVM AOT / Derby | Supported by the tested paths; no runtime class-loading experiment is required |
| Oracle GraalVM 25.0.4 Native Server / MySQL or PostgreSQL | Selected standalone All-mode paths passed |
| Oracle GraalVM 25.0.4 Native Server / embedded Derby without runtime class loading | Image compiles, but SQL execution fails |
| GraalVM CE 25.4.4.1.1 Native Server / Derby with experimental runtime class loading | Selected standalone paths passed; experimental, not a stable compatibility promise |
| Native Console / ordinary JVM Server with Derby | Selected paths passed; Derby runs in the JVM Server |

Derby 10.14.2.0 compiles SQL into activation classes at runtime and defines those new classes with
`ClassLoader.defineClass`. Reflection hints cannot supply that capability. Traditional closed-world
Native Image cannot execute this path, including the tested Oracle GraalVM 25.0.4 configuration.
Predefined-class tracing was also investigated: generated class names/bytes vary, and later SQL
can produce new classes, so it was not a maintainable replacement. Replacing the SQL engine or
moving Derby into a separate JVM would change the existing embedded-storage contract.

Consequently, embedded Derby currently requires the experimental runtime class-loading route when
compiled into the Server image. Historical GraalVM versions have not all been tested; 25.4 is not
claimed as a proven minimum. The limitation is Native execution of embedded Derby, not running
Derby with the GraalVM `java` command. The repository's Spring Boot 4 toolchain also requires
GraalVM 25+ for Native builds, independently of Derby.

The successful Derby experiment restricted preserved metadata to `org.apache.derby.iapi.*` and
`org.apache.derby.impl.sql.*`, disabled preservation of unrelated JNI, and excluded the unused
JRaft Bolt provider. It required `RuntimeClassLoading`; do not silently turn it on for ordinary
JVM builds or advertise it as stable support.

The local investigation exercised eight deployment combinations (JVM/Native merged, JVM/Native
server-only, and the four independent JVM/Native Server × Console combinations) for MySQL, Derby
and PostgreSQL on macOS ARM64. These are functional smoke results, not full API/cluster or
cross-platform certification. PR UT/IT results must be reported separately from that investigation.
